# ML-5 練習解答

完整可編譯版本：`code/solutions/ml05/`。兩個執行檔：

- `cargo run --release`：打分 API（含練習 2、3、4、5），環境變數 `FRAUD_MODEL=linear`、`FRAUD_SHADOW_MODEL=linear|mlp`
- `cargo run --release --bin ledger-with-scoring`：練習 1，第 15 章的帳本 API 加上風控

## 練習 1：整合進帳本 API

`src/bin/ledger_with_scoring.rs` 以 path 相依引用第 15 章的 `ledger` crate。`POST /transactions` 的流程：

```rust
let mut ledger = state.ledger.write().await;
if let Some(account) = debited {                                   // 存款不打分：風險在資金流出
    let raw = features_from_ledger(&ledger, account, &body.kind, amount, date, body.hour)?;
    let p = state.scorer.score(&raw)?;
    if p >= 0.9 { return Err(ApiError::Blocked { probability: p, reason: top_features(&raw) }); }   // 403
    if p >= 0.3 { pending.push(...); return Ok((StatusCode::ACCEPTED, ...)); }                        // 202，掛起
}
ledger.apply(tx)?;                                                                                   // 201
```

**特徵從帳本歷史算**：帳戶的 `log_amount` 平均與標準差、同一天的筆數當 velocity、交易前餘額。這段邏輯必須與 ML-1 的 `build()` 一致（training-serving skew）。帳本的 `Transaction` 只有日期沒有時間，所以請求額外帶 `hour`。

實測：

```
先累積 4 筆白天小額提款，然後晚上 11 點提 9,000：
{"error":"交易被風控攔截","fraud_probability":0.998,"reason":"amount_vs_acct=18.62, log_amount=9.10, velocity_24h=4.00"}   [403]

深夜把 1003 的 800 元全部提走：
{"error":"交易被風控攔截","fraud_probability":0.990,"reason":"log_amount=6.68, is_withdraw=1.00, is_night=1.00"}   [403]

白天小額：
{"balance":"49455.00","fraud_probability":1.2e-8,"id":7}   [201]
```

被擋的交易帳本沒動（1003 餘額仍是 800）。回應裡的 `reason` 是標準化後絕對值最大的三個特徵，給審核人員看「為什麼」。

一個真實的觀察：帳戶**沒有歷史**時（前三筆），`amount_vs_acct` 無法計算、模型偏寬鬆。這是冷啟動問題，實務上新帳戶會套用規則引擎（第 13 章）而不是模型，等累積足夠歷史再切換。

## 練習 2：影子模型

```rust
struct AppState {
    scorer: Arc<dyn FraudScorer>,
    shadow: Option<Arc<dyn FraudScorer>>,    // 只打分不決策
    // ...
}

if let Some(shadow) = &state.shadow {
    if let Ok(ps) = shadow.score(&raw) {
        metrics::histogram!("fraud_shadow_abs_diff").record(f64::from(ps - p).abs());
        if (ps - p).abs() > 0.3 { warn!(primary = p, shadow = ps, "主模型與影子模型分歧"); }
    }
}
```

`FRAUD_SHADOW_MODEL=linear` 啟動後，每筆請求兩個模型都打分，回應用主模型，差異進直方圖與日誌。切換新模型前先跑一兩週影子，看分歧率與分佈再決定，是模型上線的標準流程。

## 練習 3：LinearScorer 與 trait

```rust
pub trait FraudScorer: Send + Sync {
    fn score(&self, raw: &RawFeatures) -> Result<f32>;
    fn name(&self) -> &'static str;
}
impl FraudScorer for Scorer { ... }           // candle MLP
impl FraudScorer for LinearScorer { ... }     // σ(x·w + b)，10 行
```

`model/linear.json` 存 ML-2 訓練出的 9 個權重、bias，加上同一組 Scaler 參數。`LinearScorer::score` 是一個迴圈加一個 sigmoid，沒有 candle、沒有 Tensor。

```
FRAUD_MODEL=linear：{"model":"logistic (json)"}
晚上大額轉帳：p=0.508 review，66 µs
```

和 MLP 的 50 µs 差不多（延遲主要是 HTTP 與 JSON，模型本身兩者都是個位數微秒）。`Send + Sync` bound 是因為 `Arc<dyn FraudScorer>` 要跨 tokio 的執行緒（第 14 章）。
對這份資料，`LinearScorer` 就是正確的生產方案：一樣準、可解釋、沒有深度學習框架的相依。`FraudScorer` trait 讓兩者可以互換，這是第 9 章的直接應用。

## 練習 4：指標

```rust
metrics::counter!("fraud_score_requests_total", "decision" => decision).increment(1);
metrics::histogram!("fraud_score_probability").record(f64::from(p));
metrics::histogram!("fraud_score_latency_us").record(latency);
```

```
$ curl localhost:3100/metrics
fraud_score_requests_total{decision="block"} 1
fraud_score_requests_total{decision="allow"} 1
fraud_score_requests_total{decision="review"} 1
fraud_score_latency_us{quantile="0.5"} 56
fraud_score_latency_us{quantile="1"} 198
```

機率分佈的直方圖是**資料漂移**的早期警訊：某天 p 的分佈整體往上移，通常不是詐欺真的變多，而是上游的特徵計算壞了（例如金額單位從元變分）或世界變了（新產品線的交易型態不同）。比等客訴快得多。

`PrometheusBuilder::install_recorder()` 只能呼叫一次，測試會多次建 `app()`，所以用 `OnceLock` 保存 handle。

## 練習 5：三種決策的測試

```rust
#[tokio::test]
async fn night_drain_is_blocked() {
    let (status, decision, p) = decision_for(r#"{"account":1,"kind":"withdraw","amount":"48000","hour":2, ...}"#).await;
    assert_eq!((status, decision.as_str()), (StatusCode::OK, "block"), "p={p}");
}
// daytime_small_deposit_is_allowed、evening_large_transfer_goes_to_review 同理
```

用 `tower::ServiceExt::oneshot` 不開埠（第 15 章練習 2 的做法）。第四個測試 `linear_and_mlp_agree_on_extremes` 確認兩個模型對明顯案例方向一致，這是換模型時的最低安全網。

**模型測試的定位**：它們不是在驗證模型「準不準」（那是 ML-2 的評估指標的事），而是驗證「載入正確、特徵計算正確、門檻邏輯正確」。換一版權重檔，這四個測試能抓到的是部署錯誤，不是模型品質。

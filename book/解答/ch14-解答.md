## 練習 1：可重現的分片

三條規則：

1. 同一帳戶的交易永遠進同一分片，而且 bucket 按原始順序 push，所以帳戶內順序不變
2. 跨分片轉帳收集起來，**按交易 ID 排序**後單執行緒處理
3. 合併分片時帳戶按 ID 排序，確保合併順序固定

```rust
cross.sort_by_key(|t| t.id);                     // 明確的全局順序
let mut ids: Vec<&Account> = shards.iter().flat_map(|s| s.accounts()).collect();
ids.sort_by_key(|a| a.id);                       // 合併順序也固定
```

結果：

```
8 分片：拒絕 62715 筆，總額 208530546.12
8 分片再跑一次：拒絕 62715 筆，總額 208530546.12
同樣設定跑兩次相同？true
4 分片：拒絕 63176 筆，總額 211134737.27（與 8 分片相同？false）
```

**同一組設定可重現了**。但有兩個誠實的限制，寫在程式輸出裡：

- 分片數改變會改變「哪些轉帳算跨分片」，順序隨之改變，結果不同。所以**分片數是結算結果的一部分**，要跟程式版本一起記錄。
- 它與單執行緒的結果仍不同，因為跨分片轉帳被延後。要完全等價於序列處理，必須依照交易間的相依關係排程（A 的提款是否成功取決於之前轉進 A 的轉帳有沒有先處理），那是另一個層次的問題。

「可重現」與「與序列版相同」是兩件事。多數結算系統選擇前者加上明確的業務規則（例如「跨行轉帳 T+1 入帳」），而不是追求後者。

## 練習 2：rayon

```toml
[dependencies]
rayon = "1"
```

```rust
use rayon::prelude::*;
let n_seq = txs.iter().filter(|tx| verify(tx)).count();
let n_par = txs.par_iter().filter(|tx| verify(tx)).count();    // 差一個字
```

```
驗證 1000000 筆：序列 429 ms，rayon 102 ms（10 個執行緒），結果相同？true
```

4.2 倍加速，程式碼差一個字。rayon 用工作竊取（work stealing）執行緒池自動切分、負載平衡、合併。**資料平行（對一堆獨立元素做同一件事）用 rayon，不要手寫 `thread::spawn`。**
第 14 章手寫的 chunk + spawn 版本是為了教學；生產程式碼用 rayon。

注意 rayon 要求閉包是 `Sync`，並且元素型別 `Send`；`verify` 是純函式所以沒問題。如果閉包要修改共用狀態，就回到 `Arc<Mutex>` 或改用 `map` + `reduce` 的無狀態寫法。

## 練習 3：死鎖

```rust
// 執行緒 1：先 a 再 b；執行緒 2：先 b 再 a
let _gx = x.lock().unwrap();
thread::sleep(Duration::from_micros(1));     // 讓交錯更容易發生
let _gy = y.lock().unwrap();                 // 互相等對方手上的鎖
```

```
$ cargo run --release --bin settle_solutions -- --deadlock
（卡住，5 秒後仍在執行 → 強制結束）
```

程式編譯通過、沒有任何警告，然後永遠卡住。Rust 的型別系統擋資料競爭，**不擋死鎖**。

修法是固定取鎖順序：

```rust
let order = |first, second| if Arc::as_ptr(first) < Arc::as_ptr(second) { (first, second) } else { (second, first) };
let (x, y) = order(&a, &b);      // 兩個執行緒都會得到同樣的順序
```

```
固定順序取鎖：兩個執行緒各取鎖 1000 次，39 ms 完成
```

帳本的實際做法：轉帳需要鎖兩個帳戶時，按帳戶 ID 由小到大取。其他防範：鎖的範圍極短、持鎖時不呼叫可能取其他鎖的函式、用 `try_lock` 加超時偵測。

## 練習 4：執行緒數 vs 加速比

```
執行緒       ms      加速比
    1      827     0.98
    2      517     1.57
    4      270     3.01
    8      157     5.18
   16      144     5.65
```

機器有 10 個邏輯核心。觀察：

- 1 到 8 幾乎線性，8 到 16 幾乎沒變：超過核心數後執行緒只是在排隊
- 加速比上限約 5 到 6 倍，不是 10 倍：**Amdahl 定律**。驗證平行化了，但消費者的過帳是序列的；序列部分佔的比例決定了上限。要再快，必須讓過帳也平行（練習 1 的分片）
- 執行緒數的合理預設是 `thread::available_parallelism()`，rayon 與 tokio 預設都這樣做

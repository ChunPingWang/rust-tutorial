# 第 11 章練習解答

完整可編譯版本：`code/solutions/ch11/`（`cargo test` 跑 33 個測試，含 proptest）。

## 練習 1：rapid_withdrawals 的測試

```rust
#[test]
fn exactly_three_in_a_row_is_flagged() {
    assert_eq!(rapid_withdrawals(&ledger_with_withdrawals(&[1, 1, 1])), vec![1]);
}

#[test]
fn interrupted_streak_is_not_flagged() {
    assert!(rapid_withdrawals(&ledger_with_withdrawals(&[1, 1, 2, 1])).is_empty());
}

#[test]
fn long_streak_is_flagged_once() {
    assert_eq!(rapid_withdrawals(&ledger_with_withdrawals(&[2, 2, 2, 2, 2, 2])), vec![2]);
}
```

輔助函式 `ledger_with_withdrawals(&[帳戶序列])` 讓每個測試一行就能表達「什麼順序的提款」。
寫測試時發現一個設計問題：目前實作只看**提款序列**，兩筆提款中間夾一筆存款不會打斷連續。這算不算 bug 要問風控；解答裡用第四個測試**記錄**了目前的行為，之後若改規則，這個測試會提醒你。測試的一個功能就是把「目前的行為」固定下來。

## 練習 2：Statement::page 的測試

```rust
#[test] fn first_page_is_full()       // page(0, 3) → [1, 2, 3]
#[test] fn last_page_is_partial()     // 7 筆，page(2, 3) → [7]
#[test] fn page_out_of_range_is_empty() // page(3, 3)、page(100, 3) → []
```

`page` 用 `.min(len)` 夾住起點與終點，所以超出範圍不會 panic 而是空切片。這三個測試覆蓋了邊界：滿頁、不滿頁、超出。少了第三個，`&self.entries[start..end]` 在 `start > len` 時的 panic 就沒人抓。

## 練習 3：把 `>` 改成 `>=`

```
thread 'ledger::tests::withdraw_exact_balance_is_allowed' panicked
test result: FAILED. 22 passed; 1 failed
```

只有一個測試抓到：`withdraw_exact_balance_is_allowed`。它存在的理由就是這個。如果第 11 章只寫了「餘額不足要拒絕」和「餘額足夠要成功」兩個測試，這個 off-by-one 會溜過去。
**每個比較運算子值得兩個測試**：一個在邊界上、一個在邊界外。

這個手法叫**突變測試（mutation testing）**：故意改壞程式，看測試有沒有紅。沒紅的地方就是測試的漏洞。`cargo-mutants` 可以自動做這件事。

## 練習 4：`--nocapture`

```bash
cargo test --test invariants -- --nocapture
```

預設成功的測試會吞掉 `println!` 輸出，只有失敗時印出。加 `--nocapture` 全部顯示。
多執行緒跑測試時輸出會交錯，加 `--test-threads=1` 可以順序印。這在除錯測試本身的時候有用，平常不需要。

## 練習 5：proptest

```toml
[dev-dependencies]
proptest = "1"
```

```rust
fn arb_tx() -> impl Strategy<Value = Transaction> {
    let account = prop_oneof![Just(1001u32), Just(1002), Just(1003), Just(9999)];
    let kind = prop_oneof![
        account.clone().prop_map(|a| TxKind::Deposit { account: a }),
        account.clone().prop_map(|a| TxKind::Withdraw { account: a }),
        (account.clone(), account).prop_map(|(f, t)| TxKind::Transfer { from: f, to: t }),
    ];
    (any::<u64>(), 1u32..=30, kind, -10_000i64..3_000_000)
        .prop_map(|(id, day, kind, cents)| Transaction { id, day, kind, amount: Money::from_cents(cents), memo: String::new() })
}

proptest! {
    #[test]
    fn balances_never_negative_and_total_is_conserved(txs in prop::collection::vec(arb_tx(), 0..200)) {
        // ...同第 11 章的邏輯，但用 prop_assert!
    }

    #[test]
    fn failed_apply_changes_nothing(tx in arb_tx()) {
        let mut l = seeded_ledger();
        let before = l.clone();
        if l.apply(tx).is_err() {
            prop_assert_eq!(l, before);
        }
    }
}
```

比手寫 LCG 多的東西：

- **Strategy**：描述「怎麼產生輸入」，可組合（`prop_oneof!`、tuple、`prop_map`、`vec`）
- **縮小（shrinking）**：失敗時自動把輸入縮到最小反例，例如從 200 筆交易縮到「這 2 筆就會壞」
- **回歸檔**：失敗的種子存進 `proptest-regressions/`，之後每次都重跑。這個目錄應該提交到 git（解答的 `.gitignore` 為了範例乾淨排除了它，實際專案不要排除）

第二個性質「失敗的 apply 不改變任何東西」是第 6 章「先驗證再修改」的直接驗證，用隨機輸入比手寫案例涵蓋更廣。
`dev-dependencies` 只在 `cargo test` 時編譯，正式執行檔完全不含 proptest。

# 第 6 章　錯誤處理：餘額不足不是崩潰

> **場景**：結算批次每晚處理數萬筆交易。要求：
> 1. 一筆交易不合法，要被**拒絕並記錄原因**，不能讓整個批次中止
> 2. 不同原因要能被程式區分：餘額不足要通知客戶，帳戶不存在要告警給工程師
> 3. 但如果帳本總額變成負數，那是程式 bug，應該**立刻停止**，不要繼續把錯的帳寫下去

## Why：為什麼不用例外（exception）

多數語言用例外處理錯誤：`throw` 一個物件，呼叫堆疊上的某個 `catch` 接住。問題是：

- **函式簽名看不出會丟什麼**。`ledger.apply(tx)` 會丟 `InsufficientFunds` 嗎？看文件，文件可能過時。
- **很容易忘記處理**。沒 catch 的例外一路往上炸，就是「凌晨三點崩潰」。
- **控制流隱形**。一個 `throw` 可以從十層深的函式直接跳到最外層，中間的清理邏輯有沒有正確執行，很難確定。

Rust 的立場：**錯誤是值，不是控制流**。會失敗的函式回傳 `Result<T, E>`，呼叫者拿到的是一個「要嘛成功帶 T、要嘛失敗帶 E」的值，必須處理，不能忽略（編譯器會警告），而且簽名上明寫著 `E` 是什麼。

同時 Rust 區分兩種「錯」：

| | 可恢復的錯誤 | 不可恢復的錯誤 |
|---|---|---|
| 例子 | 餘額不足、檔案不存在、網路斷線、使用者輸入格式錯 | 陣列越界、整數溢位（debug）、違反程式不變量 |
| 本質 | **預期中的**失敗，是業務邏輯的一部分 | **程式 bug** |
| 機制 | `Result<T, E>` | `panic!` |
| 處理 | 呼叫者決定怎麼辦 | 程式中止（或執行緒中止），印出堆疊 |

餘額不足**不是** bug，是帳本每天都會遇到的正常情況，所以用 `Result`。
帳本總額為負**是** bug（錢憑空消失），繼續跑只會把錯誤擴大，所以 `panic!`。

## What：Result、`?`、自訂錯誤型別

### Result

和 `Option` 一樣是標準庫的 enum：

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

```rust
fn debit(&mut self, id: u32, amount: Money) -> Result<(), LedgerError>
```

讀法：成功回傳 `()`（沒有值），失敗回傳 `LedgerError`。

處理方式和 `Option` 一樣：`match`、`if let`、`map`、`unwrap_or`……另外多了幾個：

| 想做什麼 | 方法 |
|---|---|
| 成功就轉換 | `map` |
| 失敗就轉換錯誤型別 | `map_err` |
| 成功就接著做另一件可能失敗的事 | `and_then` |
| 轉成 Option（丟掉錯誤資訊） | `ok()` |
| 確定成功，否則 panic | `unwrap`、`expect("原因")` |

### `?`：錯誤傳播運算子

這是 Rust 錯誤處理不囉嗦的關鍵：

```rust
fn credit(&mut self, id: u32, amount: Money) -> Result<(), LedgerError> {
    let acct = self.find_mut(id)?;     // 如果 find_mut 回傳 Err，整個函式立刻回傳那個 Err
    ...
    Ok(())
}
```

`expr?` 等於：

```rust
match expr {
    Ok(v) => v,
    Err(e) => return Err(e.into()),   // 注意 into()：可以自動轉換錯誤型別
}
```

條件：所在函式的回傳型別必須是 `Result`（或 `Option`，對 `Option` 也能用 `?`）。
`main` 也可以回傳 `Result<(), Box<dyn Error>>`，這樣 `main` 裡也能用 `?`。

### 自訂錯誤型別

錯誤型別就是一個 enum，列出所有可能的失敗原因，每個原因帶它需要的上下文：

```rust
#[derive(Debug, Clone, PartialEq, Eq)]
enum LedgerError {
    AccountNotFound(u32),
    InsufficientFunds { account: u32, balance: Money, requested: Money },
    InvalidAmount(Money),
    SameAccountTransfer(u32),
    Overflow,
}
```

讓它成為「正式的」錯誤型別需要兩步：

```rust
use std::fmt;

// 1. 實作 Display：給人看的訊息
impl fmt::Display for LedgerError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            LedgerError::AccountNotFound(id) => write!(f, "帳戶 {id} 不存在"),
            LedgerError::InsufficientFunds { account, balance, requested } =>
                write!(f, "帳戶 {account} 餘額不足：有 {}，要 {}", balance.format(), requested.format()),
            // ...
        }
    }
}

// 2. 標記為 Error（空的 impl 即可，前提是有 Debug + Display）
impl std::error::Error for LedgerError {}
```

這是你第一次手動實作 trait。`impl Trait for Type { ... }` 的語法第 9 章會深入，這裡先照寫。

實務上大家用 `thiserror` crate 把這兩步縮成幾行屬性（第 12 章）。但先手寫一次，知道它在幫你做什麼。

### Option → Result

找不到帳戶，`find` 回傳 `None`，但 `None` 沒有說是哪個帳戶。用 `ok_or` 轉成帶資訊的錯誤：

```rust
fn find_mut(&mut self, id: u32) -> Result<&mut Account, LedgerError> {
    self.accounts
        .iter_mut()
        .find(|a| a.id == id)
        .ok_or(LedgerError::AccountNotFound(id))
}
```

### `Box<dyn Error>`：當錯誤來源很多種

解析一行文字可能遇到：欄位不夠（我們自己的錯誤）、數字格式錯（標準庫的 `ParseIntError`）。
兩種錯誤型別不同，怎麼放進同一個 `Result`？

```rust
fn parse_line(line: &str) -> Result<Transaction, Box<dyn std::error::Error>> {
    let id: u64 = parts[0].parse()?;       // ParseIntError 自動轉成 Box<dyn Error>
    if parts.len() < 3 {
        return Err(format!("欄位不足：{line:?}").into());   // String 也能轉
    }
    ...
}
```

`Box<dyn Error>` 是「任何實作了 Error trait 的東西」（第 13 章解釋 `Box`，第 9 章解釋 `dyn`）。
`?` 會自動把具體錯誤轉成它。這在應用程式的最外層（`main`、CLI 入口）很方便：你只需要印出錯誤，不需要區分它。

**什麼時候用哪個：**

- **函式庫、核心邏輯**：自訂 enum（`LedgerError`）。呼叫者需要 `match` 它做不同處理。
- **應用程式最外層**：`Box<dyn Error>`，或 `anyhow` crate（第 12 章）。只需要印出來。

### panic

```rust
assert!(total >= 0, "帳本總額為負，這是程式 bug");
panic!("不可能到這裡");
unreachable!();
let x = opt.expect("剛才已經檢查過一定有值");
```

panic 預設會展開（unwind）堆疊、呼叫所有 drop、印出訊息後中止執行緒。
用 `RUST_BACKTRACE=1 cargo run` 可以看到完整堆疊。

什麼時候該 panic：**當程式進入「不可能」的狀態時**。這代表程式有 bug，繼續執行只會讓損害擴大（帳本尤其如此）。
什麼時候不該：任何由外部輸入引起的失敗。使用者打錯、檔案壞掉、網路斷線都是 `Result`。

## How：讓帳本說清楚為什麼拒絕

完整程式碼在 `code/ch06-errors/`。

### 核心操作回傳 Result

```rust
fn credit(&mut self, id: u32, amount: Money) -> Result<(), LedgerError> {
    let acct = self.find_mut(id)?;
    let new_balance = acct.balance.0.checked_add(amount.0).ok_or(LedgerError::Overflow)?;
    acct.balance = Money(new_balance);
    Ok(())
}

fn debit(&mut self, id: u32, amount: Money) -> Result<(), LedgerError> {
    let acct = self.find_mut(id)?;
    if amount > acct.balance {
        return Err(LedgerError::InsufficientFunds {
            account: id,
            balance: acct.balance,
            requested: amount,
        });
    }
    acct.balance = Money(acct.balance.0 - amount.0);
    Ok(())
}
```

注意 `checked_add`：回傳 `Option<i64>`，溢位時是 `None`。第 1 章提過整數溢位在 release 會靜默繞回，對帳本是災難，所以每一處加法都明確檢查。

### 過帳：先驗證，再修改

```rust
fn apply(&mut self, tx: &Transaction) -> Result<(), LedgerError> {
    if tx.amount.0 <= 0 {
        return Err(LedgerError::InvalidAmount(tx.amount));
    }
    match tx.kind {
        TxKind::Deposit { account } => self.credit(account, tx.amount),
        TxKind::Withdraw { account } => self.debit(account, tx.amount),
        TxKind::Transfer { from, to } => {
            if from == to {
                return Err(LedgerError::SameAccountTransfer(from));
            }
            self.balance_of(to)?;                 // 目的帳戶存在嗎？
            self.debit(from, tx.amount)?;         // 來源扣款（可能餘額不足）
            self.credit(to, tx.amount)
                .expect("目的帳戶剛驗證過存在，溢位以外不該失敗");
            Ok(())
        }
    }
}
```

轉帳的順序是刻意的：**所有可能失敗的檢查都在第一次修改之前**。
如果先扣款再發現目的帳戶不存在，錢就消失了。這叫「先驗證再提交」，在沒有資料庫交易（transaction）的情況下是最基本的一致性手段。
最後那個 `expect` 是一個「不可能失敗」的斷言：目的帳戶剛確認存在，`credit` 唯一可能的失敗是溢位，而這代表資料本身已經壞了。

### 批次處理：一筆失敗不影響其他筆

```rust
fn run_batch(ledger: &mut Ledger, txs: &[Transaction]) -> BatchReport {
    let mut report = BatchReport::default();
    for tx in txs {
        match ledger.apply(tx) {
            Ok(()) => report.posted += 1,
            Err(e) => report.rejected.push((tx.id, e)),
        }
    }
    report
}
```

錯誤是值，所以可以收集起來、事後統計、分類通知：

```rust
for (id, err) in &report.rejected {
    if let LedgerError::InsufficientFunds { account, .. } = err {
        println!("→ 通知帳戶 {account} 的持有人：交易 #{id} 因餘額不足失敗");
    }
}
```

這就是場景需求 2：**不同原因能被程式區分**。如果錯誤只是一個字串，這裡只能用字串比對，脆弱且易錯。

### 執行結果

```
解析失敗 [7, deposit, abc, 1001]：invalid digit found in string
解析失敗 [8, refund, 100, 1001]：未知的交易種類：refund

過帳成功：2 筆，拒絕：4 筆
  交易 #3 被拒：帳戶 1002 餘額不足：有 17000.00 元，要 99999.99 元
  交易 #4 被拒：帳戶 9999 不存在
  交易 #5 被拒：不能轉帳給自己（帳戶 1001）
  交易 #6 被拒：金額不合法：-5.00 元
  → 通知帳戶 1002 的持有人：交易 #3 因餘額不足失敗
```

八筆輸入，兩筆在解析階段擋下、四筆在過帳階段拒絕、兩筆成功，程式沒有崩潰，每一筆失敗都有原因。這就是場景的三個需求。

### 試著弄壞它

1. 把 `run_batch` 裡的 `match ledger.apply(tx)` 改成只呼叫 `ledger.apply(tx);` 不處理結果。編譯器會警告 `unused Result that must be used`。這是 `#[must_use]` 屬性的效果，`Result` 自帶。
2. 把 `credit` 裡的 `?` 拿掉，看型別錯誤：你會得到 `Result<&mut Account, _>` 而不是 `&mut Account`。
3. 在 `parse_line` 裡把 `parts[3].parse()?` 的 `?` 拿掉。

## 設計筆記：錯誤型別的粒度

一個 crate 一個錯誤 enum？還是每個模組一個？經驗法則：

- **錯誤 enum 跟著「呼叫者會怎麼處理」走**。`LedgerError` 的每個變體都對應呼叫者可能採取的不同行動（通知客戶、告警、拒絕輸入）。
- 如果兩個變體呼叫者永遠會一樣處理，考慮合併。
- 解析錯誤和業務錯誤通常分開：`ParseError` 與 `LedgerError`，因為它們發生在不同階段、由不同人處理。

## 回顧

- 可恢復的錯誤用 `Result<T, E>`，程式 bug 用 `panic!`；餘額不足是前者，總額為負是後者
- `?` 把 `Err` 往上傳，程式碼只剩成功路徑，易讀
- 自訂錯誤是一個 enum + `Display` + `impl Error`；每個變體攜帶呼叫者需要的上下文
- `ok_or` 把 `Option` 變 `Result`；`Box<dyn Error>` 在最外層統一各種錯誤
- 修改狀態前先完成所有驗證，失敗時狀態才不會只改一半

## 練習

1. 新增 `LedgerError::AccountFrozen(u32)`，給 `Account` 加一個 `frozen: bool` 欄位，凍結的帳戶不能提款也不能作為轉帳來源（但可以收款）。
2. 把 `parse_line` 的錯誤改成自訂的 `ParseError` enum（至少三個變體：`MissingField`、`BadNumber`、`UnknownKind`），實作 `Display`，並用 `map_err` 把 `ParseIntError` 轉成 `BadNumber`。
3. 讓 `main` 回傳 `Result<(), Box<dyn Error>>`，把解析階段改成「任何一行解析失敗就整個 main 失敗」（用 `?`）。比較兩種策略：哪種適合夜間批次？哪種適合互動式工具？

# 第 16 章　邁向生產：效能、安全邊界、部署

> **場景**：API 跑起來了，財務也簽核了測試報告。維運團隊給了上線前的清單：
> 「執行檔要最佳化、要過靜態檢查、相依套件要掃過漏洞、要打成容器、要能從環境變數設定、崩潰要有足夠的資訊。
> 另外，資安問 Rust 是不是真的沒有記憶體漏洞，`unsafe` 是什麼？」
> 這一章把這張清單走完。沒有新的語言概念，是把前 15 章的東西變成一個可以上線的東西。

## Why：寫對只是一半

程式寫對了，不代表能上線。生產環境的要求不同：

- **效能**：debug 編譯的 Rust 比 release 慢 10 到 50 倍。第 14 章的數字如果用 debug 跑會完全失真
- **可維護**：三個月後別人（或你自己）要能看懂、能改、能相信
- **安全**：相依套件有漏洞怎麼知道？`unsafe` 用在哪裡？
- **可部署**：怎麼在沒有 Rust 工具鏈的機器上跑？
- **可觀測**：出事了怎麼知道發生什麼？

Rust 的工具鏈對這些問題有統一的答案，而且大多是 `cargo` 的子命令。

## What & How：上線清單

完整設定在 `code/ch16-production/`。

### 1. Release 編譯

```bash
cargo build --release            # 產出在 target/release/
```

debug 與 release 的差異不只是最佳化等級：debug 開啟整數溢位檢查、保留除錯符號、不內聯。**任何效能數字都要用 release 量。**

`Cargo.toml` 可以細調 release 設定：

```toml
[profile.release]
opt-level = 3        # 最高最佳化（預設）
lto = "fat"          # 連結時最佳化：跨 crate 內聯，更小更快，編譯更久
codegen-units = 1    # 更好的最佳化，編譯更慢
strip = true         # 去掉符號表
panic = "abort"      # panic 直接中止，不展開堆疊：更小更快
```

效果：`server` 執行檔 1.4MB，`ledger` CLI 734KB，**不需要任何執行環境**。對比 Node.js 或 Python 的部署（要帶整個 runtime），這是 Rust 最被低估的優點。

`panic = "abort"` 要想清楚：panic 時不會跑 `Drop`，鎖不會釋放、檔案不會 flush。對「崩潰就重啟」的服務是對的；對需要在 panic 時清理的程式不是。

另一個實用設定：

```toml
[profile.dev.package."*"]
opt-level = 2        # 開發時相依套件也最佳化，自己的程式碼仍是 debug。測試快很多
```

### 2. clippy：比編譯器多想一步

```bash
cargo clippy --all-targets
```

clippy 是官方的 lint 工具，有 700 多條規則：效能（不必要的 clone）、慣用寫法（手寫的迴圈可以用迭代器）、正確性（可能的溢位）。
對第 16 章的程式碼跑一次，它找到五個：

```
warning: writing `&PathBuf` instead of `&Path` involves a new object where a slice will do
warning: the following explicit lifetimes could be elided: 'b
warning: manual implementation of `.is_multiple_of()`
warning: consider using `sort_by_key`
```

每一條都是第 3 章（`&Path` 比 `&PathBuf` 通用，和 `&str` vs `&String` 同理）、第 10 章（多餘的生命週期）的知識。clippy 是免費的 code review。
CI 裡用 `cargo clippy -- -D warnings` 讓警告變成錯誤。

### 3. rustfmt：不要吵排版

```bash
cargo fmt              # 排版
cargo fmt --check      # CI 用：有未排版的檔案就失敗
```

Rust 社群幾乎一致使用 rustfmt 的預設設定。團隊不需要討論縮排與括號位置。本書所有範例程式碼都經過 `cargo fmt`。

### 4. 相依套件稽核

```bash
cargo install cargo-audit
cargo audit                      # 對照 RustSec 漏洞資料庫檢查 Cargo.lock

cargo install cargo-deny
cargo deny check                 # 授權、重複相依、來源白名單
```

`cargo audit` 應該在 CI 每天跑一次（不只在 push 時），因為漏洞是事後才被揭露的。
`cargo tree -d` 列出被多個版本重複引入的套件，是減少執行檔大小與編譯時間的切入點。

### 5. `unsafe`：安全邊界在哪裡

資安問的問題值得認真回答。

Rust 的記憶體安全保證來自編譯器的檢查。但有些事編譯器證明不了：呼叫 C 函式庫、直接操作硬體、實作標準庫的 `Vec` 內部。這些地方需要 `unsafe`：

```rust
pub fn bytes_as_u32(bytes: &[u8]) -> Option<&[u32]> {
    if !bytes.len().is_multiple_of(4) { return None; }
    if bytes.as_ptr().align_offset(align_of::<u32>()) != 0 { return None; }
    // SAFETY: 上面檢查了長度與對齊；u32 沒有無效位元模式；借用規則由輸入的 &[u8] 延續。
    let slice = unsafe { std::slice::from_raw_parts(bytes.as_ptr().cast::<u32>(), bytes.len() / 4) };
    Some(slice)
}
```

`unsafe` 區塊的意思是：**「編譯器，這裡我負責」**。它解鎖五件事：解引用裸指標、呼叫 unsafe 函式、存取可變靜態變數、實作 unsafe trait、存取 union 欄位。它**不會**關掉借用檢查或型別檢查。

重點是**安全抽象**：unsafe 區塊被包在一個安全的函式裡，函式自己檢查所有前提（長度、對齊），呼叫者不需要也不能寫 unsafe。
`Vec`、`String`、`Mutex` 內部都有 unsafe，但你用了 15 章一次都沒寫，就是這個設計的結果。

回答資安：

- 本書的 `ledger` 除了這個示範模組，**沒有任何 unsafe**。`grep -rn unsafe src/` 可以驗證
- 相依套件裡有（tokio、serde 都有，為了效能），但它們是被最多人審查的 Rust 程式碼
- `cargo geiger` 可以統計整個相依樹的 unsafe 用量
- 每個 unsafe 區塊都應該有 `// SAFETY:` 註解說明為什麼安全。clippy 的 `undocumented_unsafe_blocks` lint 可以強制

Rust 的保證是：**只要所有 unsafe 區塊都正確，整個程式就沒有記憶體安全問題**。審查範圍從「所有程式碼」縮小到「unsafe 區塊」。這是與 C/C++ 的本質差異。

### 6. 容器化

```dockerfile
# 階段一：編譯
FROM rust:1.90-bookworm AS builder
WORKDIR /app
COPY Cargo.toml Cargo.lock ./
RUN mkdir -p src/bin && echo 'fn main() {}' > src/main.rs \
    && echo 'fn main() {}' > src/bin/server.rs && echo '' > src/lib.rs \
    && cargo build --release --bin server && rm -rf src      # 先編相依，讓這層被快取
COPY src ./src
RUN touch src/lib.rs src/bin/server.rs && cargo build --release --bin server

# 階段二：執行
FROM gcr.io/distroless/cc-debian12
COPY --from=builder /app/target/release/server /usr/local/bin/ledger-server
ENV LEDGER_ADDR=0.0.0.0:3000
USER nonroot
ENTRYPOINT ["/usr/local/bin/ledger-server"]
```

兩個重點：

- **多階段建置**：最終映像只有執行檔與 glibc，實測 50MB（distroless 基底約 48MB + 執行檔 1.4MB），沒有編譯器、沒有 shell。攻擊面最小
- **相依快取**：先複製 `Cargo.toml`/`Cargo.lock` 用假的 main 編譯一次，相依套件的編譯結果被 Docker 層快取。之後只改程式碼時，重建只需要編譯自己的 crate

實際建置與驗證：

```
$ docker build -t ledger-server:ch16 .
$ docker run -d --rm -p 3016:3000 ledger-server:ch16
$ curl localhost:3016/accounts/1001
{"id":1001,"owner":"王小明","balance":"50000.00","balance_cents":5000000}
$ docker inspect ledger-ch16 --format '{{.Config.User}}'
nonroot
```

想要更小，可以用 `--target x86_64-unknown-linux-musl` 靜態連結，產出的執行檔可以放進 `FROM scratch`（0 bytes 的基底），映像只剩執行檔本身。

### 7. 設定與秘密

```rust
let addr = std::env::var("LEDGER_ADDR").unwrap_or_else(|_| "127.0.0.1:3000".to_string());
```

十二要素應用（12-factor）的原則：設定從環境變數來，不寫死、不放在程式碼庫。
複雜一點用 `config` crate（支援檔案 + 環境變數 + 預設值的分層），或用 clap 的 `env` 功能讓命令列參數也能從環境變數讀。

秘密（資料庫密碥、API key）絕不進 git，絕不印進日誌。`secrecy` crate 提供一個 `SecretString` 型別，`Debug` 輸出是 `[REDACTED]`，防止不小心 `{:?}` 印出來。

### 8. 可觀測性

第 15 章用了 `tracing`。生產環境再加三件事：

- **JSON 格式輸出**：`tracing_subscriber::fmt().json()`，讓日誌系統可以解析欄位
- **請求追蹤**：每個請求一個 span 帶 request id，所有日誌自動附上，跨服務時用 OpenTelemetry 串起來
- **指標**：`metrics` crate + Prometheus exporter，記錄請求數、延遲分佈、拒絕原因分佈。第 6 章的 `LedgerError` enum 在這裡再次回報：每個變體是一個指標標籤

panic 的處理：`std::panic::set_hook` 可以在崩潰前把 panic 訊息送進日誌系統；`RUST_BACKTRACE=1` 讓堆疊可見。
`panic = "abort"` 的設定下，panic hook 仍然會被呼叫，然後程式中止。

### 9. 效能分析

量測，不要猜。工具：

| 工具 | 用途 |
|---|---|
| `cargo bench` + criterion crate | 微基準測試，統計顯著性 |
| `cargo flamegraph` | 火焰圖，看時間花在哪 |
| `perf` / Instruments | 系統層的 profiler |
| `cargo bloat` | 執行檔哪些函式佔空間 |
| `dhat` / `heaptrack` | 堆積配置分析 |

第 14 章的經驗：大鎖比單執行緒慢。沒有量測，直覺會告訴你「多執行緒一定快」。

常見的 Rust 效能問題，依出現頻率：

1. 不必要的 `clone()`（第 2、3 章）
2. 在迴圈裡配置（每圈 `String::new()`、`Vec::new()`）：移到迴圈外重用
3. `HashMap` 的預設雜湊函式（防 DoS 但慢）：確定 key 不來自外部時換 `FxHashMap`
4. 鎖的範圍太大（第 14 章）
5. debug 編譯

### 10. CI 清單

一個最小的 GitHub Actions 流程：

```yaml
- run: cargo fmt --check
- run: cargo clippy --all-targets -- -D warnings
- run: cargo test
- run: cargo audit
- run: cargo build --release
```

五行，涵蓋排版、lint、測試、漏洞、建置。全綠才能合併。

## 回顧整本書

從第 1 章一個印出餘額的 `main`，到現在一個有 CLI、有 API、有 34 個測試、能打成 30MB 容器的服務。回頭看每一章的「Why」，它們其實是同一個主題的不同面向：

| 事故 | 擋住它的機制 | 章節 |
|---|---|---|
| 浮點數讓帳對不起來 | `Money(i64)` newtype，型別系統拒絕 `Money + u32` | 1、4 |
| 兩個執行緒同時改餘額 | `Send`/`Sync`，沒有鎖就不能跨執行緒 | 3、14 |
| null 沒檢查凌晨崩潰 | `Option`/`Result`，必須處理才能編譯 | 5、6 |
| 有人繞過驗證直接改餘額 | 私有欄位 + `pub(crate)` | 8 |
| 新增一種交易忘了處理 | `match` 窮舉 | 5 |
| 失敗的轉帳只扣了一半 | 先驗證再修改，測試驗證狀態未改壞 | 6、11 |
| 對帳單指向已刪除的帳戶 | 生命週期 | 10 |
| 整數溢位靜默繞回 | `checked_add`，溢位是 `Result` | 1、6 |

Rust 的設計哲學一句話：**把執行期的錯誤搬到編譯期**。學習曲線陡，是因為編譯器要求你在寫程式時就把這些問題想清楚。
但「想清楚」本來就是寫帳本系統該做的事。Rust 只是不讓你跳過它。

## 練習

1. 在 `ch16-production` 跑 `cargo build --release`，再把 `[profile.release]` 的 `lto` 與 `strip` 註解掉重建，比較執行檔大小。
2. `cargo install cargo-audit && cargo audit`。有沒有已知漏洞？（教材撰寫時沒有，但你讀到時可能有，這就是為什麼它要每天跑。）
3. 把 `Dockerfile` 真的建起來：`docker build -t ledger-server .`，然後 `docker run -p 3000:3000 ledger-server`，用 curl 打 API。看映像大小。
4. 用 `cargo clippy -- -W clippy::pedantic` 開啟更嚴格的規則集，看看它對 `ledger` 有什麼意見。哪些你同意？哪些你會關掉？
5. 加 `metrics` crate，為每一種 `LedgerError` 變體記一個 counter。思考：這個 `match` 應該放在哪一層（core / CLI / API）？

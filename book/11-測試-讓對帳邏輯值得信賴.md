# 第 11 章　測試：讓對帳邏輯值得信賴

> **場景**：財務主管看完 demo 後說：「很好。現在請證明給我看：轉帳失敗時來源帳戶絕對不會被扣款；
> 任何情況下餘額不會變負；總額永遠守恆。不是用嘴巴說，是每次改程式都自動驗證。」
> 這是上線前的硬性要求。

## Why：為什麼 Rust 的測試值得特別講

測試不是 Rust 特有的概念，但 Rust 有幾個讓測試特別順手的設計：

- **測試框架內建**。不用選套件、不用設定，`#[test]` 加 `cargo test` 就跑。
- **單元測試和程式碼在同一個檔案**，可以測私有函式，而且改程式時測試就在旁邊。
- **文件裡的範例會被當測試執行**。文件不會過時，因為過時就會紅。
- **型別系統已經擋掉一大類測試**。你不需要測「傳 null 進去會怎樣」「兩個執行緒同時改會怎樣」，編譯器處理了。所以 Rust 的測試可以集中在**業務規則**上。

對帳本來說，最後一點最重要：測試的每一行都在驗證財務規則，而不是在防禦語言的坑。

## What：三種測試

### 單元測試：`#[cfg(test)] mod tests`

```rust
// src/money.rs 的最下面
#[cfg(test)]
mod tests {
    use super::*;      // 把外層所有東西（包括私有的）帶進來

    #[test]
    fn from_yuan_multiplies_by_100() {
        assert_eq!(Money::from_yuan(12).cents(), 1_200);
    }

    #[test]
    #[should_panic(expected = "Money 加法溢位")]
    fn add_operator_panics_on_overflow() {
        let _ = Money::from_cents(i64::MAX) + Money::from_cents(1);
    }

    #[test]
    fn internal_representation_is_cents() {
        assert_eq!(Money::from_yuan(1).0, 100);     // .0 是私有的，只有這裡能碰
    }
}
```

- `#[cfg(test)]`：這個模組只在 `cargo test` 時編譯，正式執行檔裡沒有它
- `#[test]`：標記一個測試函式。無參數、無回傳（或回傳 `Result`）
- `#[should_panic(expected = "...")]`：預期會 panic，且訊息要包含該字串
- `#[ignore]`：暫時跳過，`cargo test -- --ignored` 才跑

斷言巨集：

| 巨集 | 用途 |
|---|---|
| `assert!(cond, "訊息 {x}")` | 條件為真 |
| `assert_eq!(a, b)` | 相等，失敗時印出兩邊的值（需要 `Debug + PartialEq`） |
| `assert_ne!(a, b)` | 不相等 |
| `matches!(x, Pattern)` 搭配 `assert!` | 比對形狀而不比對完整值 |

測試函式可以回傳 `Result<(), E>`，這樣裡面可以用 `?`：

```rust
#[test]
fn deposit_works() -> Result<(), LedgerError> {
    let mut l = Ledger::new();
    l.open(1, "甲", Money::ZERO)?;
    l.apply(tx(1, TxKind::Deposit { account: 1 }, 100))?;
    assert_eq!(l.balance_of(1)?, Money::from_cents(100));
    Ok(())
}
```

### 整合測試：`tests/` 目錄

```
tests/
├── common/
│   └── mod.rs         # 共用輔助程式，用目錄形式才不會被當成測試檔
├── ledger_flow.rs     # 每個 .rs 是一個獨立的 crate
└── invariants.rs
```

```rust
// tests/ledger_flow.rs
mod common;
use common::{seeded_ledger, tx};
use ledger::{LedgerError, Money, TxKind};     // 只能用公開 API

#[test]
fn end_to_end_batch_then_report() { ... }
```

整合測試從**外部使用者的角度**測試 crate：只能用 `pub` 的東西。這有個好處：如果你發現測試寫不出來，通常代表公開 API 設計有問題。
整合測試只對 library crate 有效，這是第 8 章把邏輯放進 lib 的另一個理由。

### 文件測試：`///` 裡的程式碼區塊

```rust
/// 金額（分）。
///
/// # 範例
///
/// ```
/// use ledger::Money;
/// let a = Money::from_yuan(100);
/// assert_eq!((a + Money::from_cents(50)).cents(), 10_050);
/// ```
pub struct Money(i64);
```

`cargo test` 會把每個程式碼區塊包進一個 `fn main()` 編譯執行。文件測試也是從外部視角（要 `use ledger::Money`）。
想隱藏樣板行用 `# ` 前綴：`# use ledger::Money;` 會執行但不顯示在文件裡。

### 執行

```bash
cargo test                        # 全部
cargo test money                  # 名稱含 money 的
cargo test --lib                  # 只跑單元測試
cargo test --test ledger_flow     # 只跑某個整合測試檔
cargo test --doc                  # 只跑文件測試
cargo test -- --nocapture         # 顯示 println! 輸出（預設成功的測試會吞掉輸出）
cargo test -- --test-threads=1    # 單執行緒跑（測試預設平行執行）
```

測試預設**平行執行**。所以測試之間不能共用可變狀態（例如同一個檔案路徑）。`storage_round_trip_preserves_ledger` 用了 `process::id()` 讓檔名唯一，就是為了這個。

## How：證明財務規則

完整程式碼在 `code/ch11-testing/`。`cargo test` 會跑 24 個測試：16 個單元、6 個整合、2 個文件。

### 從需求到測試名稱

財務主管的三個要求直接變成三個測試：

```rust
#[test]
fn transfer_to_missing_account_does_not_debit_source() {
    let mut l = ledger_with_two_accounts();
    let err = l.apply(tx(1, TxKind::Transfer { from: 1, to: 999 }, 3_000)).unwrap_err();
    assert_eq!(err, LedgerError::AccountNotFound(999));
    assert_eq!(l.balance_of(1).unwrap(), Money::from_yuan(100), "失敗的轉帳不能扣款");
}

#[test]
fn transfer_moves_money_and_preserves_total() {
    let mut l = ledger_with_two_accounts();
    let before = l.total_balance();
    l.apply(tx(1, TxKind::Transfer { from: 1, to: 2 }, 3_000)).unwrap();
    assert_eq!(l.total_balance(), before, "轉帳不能改變總額");
}
```

測試名稱寫成一句話，描述**規則**而不是**動作**。失敗時光看名稱就知道哪條規則破了。

### 測試邊界

```rust
#[test]
fn withdraw_exact_balance_is_allowed() { ... }         // 剛好等於餘額：要成功
#[test]
fn withdraw_more_than_balance_is_rejected_and_not_recorded() { ... }  // 多一分：要失敗
```

`>` 和 `>=` 寫錯是最常見的 bug，而且只有邊界測試抓得到。每一個比較運算子，都值得兩個測試。

### 測試錯誤路徑

錯誤路徑的測試常被忽略，但對帳本來說它們比成功路徑更重要：

```rust
#[test]
fn deposit_overflow_is_an_error_not_a_panic() {
    let mut l = Ledger::new();
    l.open(1, "甲", Money::from_cents(i64::MAX - 10)).unwrap();
    assert_eq!(l.apply(tx(1, TxKind::Deposit { account: 1 }, 100)), Err(LedgerError::Overflow));
    assert_eq!(l.balance_of(1).unwrap(), Money::from_cents(i64::MAX - 10));   // 餘額沒變
}
```

注意每個錯誤測試都有兩個斷言：**錯誤正確**，而且**狀態沒被改壞**。第 6 章「先驗證再修改」的設計，在這裡被驗證。

這也是為什麼 `LedgerError` 要 derive `PartialEq`：讓 `assert_eq!` 能直接比對整個錯誤值。

### 不變量測試：隨機輸入 + 永遠成立的性質

```rust
// tests/invariants.rs
#[test]
fn balances_never_negative_and_total_is_conserved() {
    for seed in 0..20u64 {
        let mut rng = Lcg(seed);
        let mut l = seeded_ledger();
        let mut expected_total = l.total_balance();
        for id in 1..=500u64 {
            let tx = random_tx(&mut rng, id);        // 隨機種類、隨機帳戶（含不存在的）、隨機金額（含負數）
            // ...
            if l.apply(tx).is_ok() { expected_total = ...; }
        }
        for acct in l.accounts() {
            assert!(acct.balance() >= Money::ZERO);
        }
        assert_eq!(l.total_balance(), expected_total);
    }
}
```

這是**屬性式測試（property-based testing）**的思路：不寫「輸入 X 應該得到 Y」，而是寫「無論輸入什麼，Z 永遠成立」。
一萬筆隨機交易（20 個種子 × 500 筆），任何一筆讓餘額變負或總額不守恆，測試就紅。
範例為了不引入外部套件自己寫了一個 LCG 隨機數產生器；正式專案用 `proptest` crate，它還會在失敗時自動縮小輸入找最小反例。

### 共用的測試輔助

```rust
// tests/common/mod.rs
#![allow(dead_code)]      // 不是每個測試檔都用到所有輔助函式
pub fn seeded_ledger() -> Ledger { ... }
pub fn tx(id: u64, day: u32, kind: TxKind, yuan: i64) -> Transaction { ... }
```

單元測試裡也有 `ledger_with_two_accounts()` 和 `tx()`。測試程式碼和正式程式碼一樣要避免重複，但**可讀性優先於去重**：一個測試從頭到尾看得懂，比抽成五層輔助函式好。

### 測試替身：InMemoryStorage

```rust
let mut mem = InMemoryStorage::default();
mem.save(&l).unwrap();
assert_eq!(mem.load().unwrap(), l);
```

第 9 章抽出 `Storage` trait 的回報：測試不需要碰磁碟。等到第 15 章有 API 伺服器時，可以注入 `InMemoryStorage` 測試整個請求流程，不需要資料庫。

## 測試的組織原則

| 測什麼 | 放哪裡 | 原因 |
|---|---|---|
| 單一型別的行為（`Money` 的格式、溢位） | 單元測試，同檔案 | 需要碰私有欄位，改程式時測試就在旁邊 |
| 單一模組的業務規則（`Ledger::apply` 的每條規則） | 單元測試，同檔案 | 同上 |
| 跨模組的流程（過帳 → 報表 → 存檔） | 整合測試 `tests/` | 從使用者視角，驗證公開 API 組合起來正確 |
| 不變量 | 整合測試 | 需要大量隨機操作，獨立成檔好管理 |
| API 使用範例 | 文件測試 | 讀者看到的範例保證能跑 |

## 回顧

- `#[cfg(test)] mod tests` + `#[test]`，`cargo test` 一行跑全部
- 單元測試能碰私有項目；整合測試只能用公開 API，等於在驗證 API 設計
- 文件範例是測試，不會過時
- 每個比較運算子值得兩個邊界測試；每個錯誤路徑驗證「錯誤正確」且「狀態未改壞」
- 不變量測試：隨機輸入 + 永遠成立的性質，比列舉案例更能抓到意外
- 測試平行執行，不要共用檔案路徑等可變狀態

## 練習

1. 給 `report::rapid_withdrawals` 寫測試：剛好三筆連續（要標記）、兩筆連續加一筆別的帳戶再一筆（不標記）、六筆連續（只標記一次）。
2. 給 `Statement::page` 寫測試：第一頁、最後一頁不滿、超出範圖的頁數回傳空切片。
3. 把 `Ledger::debit` 的 `amount > acct.balance()` 改成 `>=`，跑 `cargo test`，看哪個測試抓到了。改回來。
4. 用 `cargo test -- --nocapture` 跑不變量測試，加一行 `println!` 印出每個種子最後的總額，觀察測試輸出的行為。
5. （進階）在 `Cargo.toml` 加 `[dev-dependencies] proptest = "1"`，把 `invariants.rs` 改用 `proptest!` 巨集。注意 `dev-dependencies` 只在測試時編譯，不會進正式執行檔。

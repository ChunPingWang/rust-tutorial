# 第 14 章　並行：多執行緒結帳不出錯

> **場景**：夜間結算要處理百萬筆交易，每筆都要跑簽章驗證與風控規則，單執行緒要跑十分鐘。機器有 10 核。
> 前言的事故二就是在這裡發生的：舊系統用多執行緒加速，兩個執行緒同時更新同一帳戶，一筆入帳消失。
> 我們要加速，但這次要讓「兩個執行緒同時改同一筆資料」**無法編譯**。

## Why：為什麼 Rust 的並行是「無畏的」

資料競爭（data race）需要三個條件同時成立：

1. 兩個以上執行緒存取同一塊記憶體
2. 至少一個是寫入
3. 沒有同步機制

第 3 章的借用規則已經在單執行緒禁止了「同時有 `&mut` 和其他引用」。Rust 把這條規則延伸到執行緒：**能跨執行緒分享的型別，必須在型別系統裡證明它是安全的**。
證明的方式是兩個 marker trait：

- `Send`：這個型別的值可以**移動**到另一個執行緒
- `Sync`：這個型別的引用 `&T` 可以在多個執行緒間**分享**（等價於 `&T: Send`）

編譯器自動推導：由 `Send` 欄位組成的型別是 `Send`，依此類推。`Rc` 不是 `Send`（計數非原子），`RefCell` 不是 `Sync`（借用標記非原子），`Mutex<T>` 是 `Sync`（只要 `T: Send`）。
`thread::spawn` 要求閉包是 `Send + 'static`，所以任何試圖把 `Rc<RefCell<Ledger>>` 送進執行緒的程式碼都會被拒絕。

「無畏並行（fearless concurrency）」的意思不是沒有 bug，而是**沒有資料競爭這一類 bug**。死鎖、邏輯錯誤、順序問題仍然是你的責任，這章後半會談。

## What：執行緒、共享狀態、訊息傳遞

### 建立執行緒

```rust
let handle = thread::spawn(move || {
    // 這個閉包在新執行緒執行
    // move：把用到的外部變數的所有權搬進來
    42
});
let result = handle.join().unwrap();    // 等待結束，拿回傳值；執行緒 panic 時 join 回傳 Err
```

`move` 幾乎永遠需要：新執行緒可能比建立它的函式活得久，所以不能借用外面的變數（`'static` 要求）。

### `thread::scope`：可以借用的執行緒

```rust
thread::scope(|s| {
    s.spawn(|| println!("{}", ledger.total_balance()));    // 借用 ledger，不用 Arc
    s.spawn(|| println!("{}", ledger.history().len()));
});    // scope 結束前保證所有執行緒 join，所以借用安全
```

當你只是想「把一批工作平行跑完再繼續」，`scope` 比 `spawn` + `Arc` 簡潔得多。

### `Arc<Mutex<T>>`：第 13 章的多執行緒版

| 單執行緒 | 多執行緒 | 差別 |
|---|---|---|
| `Rc<T>` | `Arc<T>` | Atomic 計數 |
| `RefCell<T>` | `Mutex<T>` | 違反規則時：panic → **等待** |
| `.borrow_mut()` | `.lock().unwrap()` | 回傳 `MutexGuard`，drop 時解鎖 |
| `.borrow()` | `.lock().unwrap()` | Mutex 不分讀寫；要分用 `RwLock` |

```rust
let shared = Arc::new(Mutex::new(ledger));
let handles: Vec<_> = chunks.into_iter().map(|chunk| {
    let shared = Arc::clone(&shared);
    thread::spawn(move || {
        for tx in chunk {
            let mut ledger = shared.lock().unwrap();     // 取鎖
            ledger.apply(tx);
        }                                                 // guard drop → 解鎖
    })
}).collect();
```

`lock()` 回傳 `Result`，`Err` 表示有另一個執行緒在持鎖時 panic 了（鎖「中毒」）。`unwrap()` 是常見做法：如果別人崩潰了，我也崩潰。

**鎖的範圍越小越好。** `MutexGuard` 活著的每一毫秒，其他執行緒都在排隊。驗證、解析這類不需要帳本的工作，放在取鎖之前。

### `RwLock<T>`：多讀者、單寫者

```rust
let shared = Arc::new(RwLock::new(ledger));
let r = shared.read().unwrap();      // 多個 read 可以同時持有
let w = shared.write().unwrap();     // write 獨佔
```

適合「查詢遠多於修改」的場合，例如 API 伺服器（下一章）。

### Channel：用溝通來分享

```rust
let (sender, receiver) = mpsc::channel::<Transaction>();
// 多個生產者
for chunk in chunks {
    let sender = sender.clone();                 // mpsc = multi-producer, single-consumer
    thread::spawn(move || for tx in chunk { sender.send(tx).unwrap(); });
}
drop(sender);                                    // 關鍵：主執行緒的 sender 也要丟掉
// 一個消費者
for tx in receiver {                             // 所有 sender 都 drop 後迴圈結束
    ledger.apply(tx);
}
```

這是 Go 的哲學「不要透過共享記憶體來溝通，透過溝通來共享記憶體」。帳本只有一個執行緒碰，**不需要鎖**。
前置工作（驗證）在多個生產者平行做，過帳在消費者序列做。只要前置工作比過帳重，就有加速。

送進 channel 的值所有權會移動（第 2 章），所以不會有兩個執行緒同時持有同一筆交易。

### 原子型別

計數器、旗標這類簡單狀態不需要 Mutex：

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
let counter = Arc::new(AtomicUsize::new(0));
counter.fetch_add(1, Ordering::Relaxed);
```

`Ordering` 是記憶體順序，計數器用 `Relaxed` 就好；需要「這個寫入對其他執行緒可見之後才做下一件事」時用 `SeqCst`。超出本書範圍。

## How：四種結算策略與一次誠實的量測

完整程式碼在 `code/ch14-concurrency/src/bin/settle.rs`。執行 `cargo run --release --bin settle`（一定要 `--release`，debug 模式的數字沒有意義）。

每筆交易先過 `verify()`（模擬簽章驗證的 CPU 工作，約 0.4 微秒），再 `apply()`。一萬個帳戶，一百萬筆交易，8 個工作執行緒，10 核的機器：

```
[單執行緒]           412 ms，拒絕 70355 筆，總額 219919229.58
[Arc<Mutex> 大鎖]     527 ms，拒絕 70353 筆，總額 220517921.47
[channel 單寫者]      188 ms，拒絕 70325 筆，總額 220407453.13
[分片 ×8]            173 ms，拒絕 62715 筆，總額 208530546.12（跨分片轉帳 293063 筆另外處理）
[RwLock 讀者 ×8]       55 ms
```

三個觀察，每個都是真實系統裡會遇到的：

### 觀察一：大鎖比單執行緒慢

8 個執行緒搶同一把鎖。驗證是平行的，但過帳是序列的，加上鎖的競爭與 cache 失效，整體比單執行緒還慢。
**並行不等於變快。** 如果共享狀態是瓶頸，加執行緒只是加排隊的人。

### 觀察二：channel 快 2 倍

驗證（重）平行、過帳（輕）序列，而且帳本不需要鎖。這是「把可平行的部分和必須序列的部分分開」的典型做法。加速比受限於序列部分的比例（Amdahl 定律）。

### 觀察三：分片的結果**不同**

分片版本拒絕的筆數少了八千筆，總額也不同。這不是 bug。
同一帳戶的提款，誰先到決定誰被拒。分片把跨分片的轉帳抽出來最後處理，改變了順序，結果就變了。前兩種平行模式的結果其實也和單執行緒**微幅**不同（70355 vs 70353 vs 70325），原因相同：執行緒的交錯順序不確定。

這對金融系統是致命的：**結算結果必須可重現**。所以真正可用的平行化，必須保證：

- 同一帳戶的交易順序不變
- 跨分片的交易有明確的全局排序規則
- 跑兩次得到同樣的結果

這些是業務規則，編譯器幫不了你。Rust 保證的是「不會有資料競爭讓一筆入帳憑空消失」；「哪個順序才正確」是你要先定義的。並行的第一步不是寫 `thread::spawn`，是定義「什麼叫正確」。

### 編譯器擋住的東西

程式碼最後有三段註解掉的程式，請一個一個打開：

```rust
// (a) 移進執行緒後還想用
let mut plain = ledger.clone();
thread::spawn(move || plain.apply(tx));
plain.total_balance();
// error[E0382]: borrow of moved value: `plain`

// (b) 第 13 章的 Rc<RefCell<>>
let rc = Rc::new(RefCell::new(ledger.clone()));
let rc2 = Rc::clone(&rc);
thread::spawn(move || rc2.borrow_mut().total_balance());
// error[E0277]: `Rc<RefCell<Ledger>>` cannot be sent between threads safely
//   = help: the trait `Send` is not implemented for `Rc<RefCell<Ledger>>`

// (c) 把鎖的 guard 送到別的執行緒
let guard = shared.write().unwrap();
thread::spawn(move || drop(guard));
// error[E0277]: `MutexGuard<'_, Ledger>` cannot be sent between threads safely
```

(b) 就是前言事故二在 Rust 的下場：想在兩個執行緒共享可變狀態卻沒有鎖，編譯不過。
錯誤訊息直接告訴你缺的是 `Send`，而 `Arc<Mutex<T>>` 就是為了滿足它而存在的。

## 死鎖：Rust 不會幫你擋的

```rust
let a = Arc::new(Mutex::new(ledger_a));
let b = Arc::new(Mutex::new(ledger_b));
// 執行緒 1
let ga = a.lock(); let gb = b.lock();
// 執行緒 2
let gb = b.lock(); let ga = a.lock();    // 死鎖：互相等對方
```

這會編譯通過。防範方法是紀律：**總是以相同順序取鎖**（例如按帳戶 ID 由小到大）、鎖的範圍極短、不要在持鎖時呼叫可能取其他鎖的函式。
轉帳需要同時鎖兩個帳戶時，先排序 `(min(from, to), max(from, to))` 再依序取鎖，是標準做法。

## 什麼時候用哪個

| 情境 | 用 |
|---|---|
| 一批獨立工作平行跑完 | `thread::scope` 或 rayon crate 的 `par_iter()` |
| 多個執行緒偶爾改同一狀態 | `Arc<Mutex<T>>`，鎖範圍極短 |
| 讀多寫少 | `Arc<RwLock<T>>` |
| 生產者-消費者、管線 | `mpsc::channel`（或 crossbeam crate 的更快版本） |
| 簡單計數器、旗標 | `Atomic*` |
| 大量 I/O 等待（網路、檔案） | 非同步（下一章），不是執行緒 |

rayon 值得特別一提：`txs.par_iter().filter(verify).count()` 一行就把迭代器平行化，自動處理執行緒池與工作分配。資料平行的首選。

## 回顧

- `Send`/`Sync` 讓「能不能跨執行緒」成為型別的一部分，資料競爭是編譯錯誤
- `Rc<RefCell<>>` → `Arc<Mutex<>>`；違反規則從 panic 變成等待；guard drop 即解鎖，範圔越小越好
- channel 讓狀態只有一個擁有者，不需要鎖；`thread::scope` 讓執行緒可以借用
- 並行不一定快：共享狀態是瓶頸時，加執行緒只是加排隊
- 並行會改變順序，結果可能不同；可重現性是業務規則，要先定義才能平行化
- 死鎖編譯器不擋：固定取鎖順序

## 練習

1. 把分片版本改成「同一帳戶的交易一定在同一分片、且順序不變，跨分片轉帳以交易 ID 排序後處理」，驗證跑兩次結果相同。
2. 加入 rayon（`cargo add rayon`），用 `txs.par_iter().filter(|tx| verify(tx)).count()` 取代手寫的執行緒，比較程式碼長度與速度。
3. 寫一個會死鎖的小程式（兩個 Mutex，兩個執行緒反向取鎖），親眼看它卡住。然後用「固定順序取鎖」修好。
4. 把 `WORKERS` 改成 1、2、4、8、16，記錄 channel 模式的時間，畫出加速比曲線。到幾個執行緒之後不再變快？為什麼？
